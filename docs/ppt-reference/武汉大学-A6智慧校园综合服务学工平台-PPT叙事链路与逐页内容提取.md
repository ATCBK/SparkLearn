## 一、原 PPT 的一句话叙事

这套 PPT 的核心讲法是：先用政策背景、市场趋势和校园管理痛点证明“智慧校园学工平台有必要做”，再用六大模块、六类角色、两端适配和多源数据证明“平台做得很全”，随后展示代表性功能，最后用四项关键技术和四个工程特色收束成“有技术、有创新、有落地基础”的竞赛项目。

## 二、原 PPT 的整体链路

```mermaid
flowchart LR
    A["政策背景与市场增长"] --> B["行业现状与竞品分析"]
    B --> C["校园管理痛点"]
    C --> D["数据、功能、用户、性能需求"]
    D --> E["平台总体介绍"]
    E --> F["系统框架与角色功能结构"]
    F --> G["六大模块全景展示"]
    G --> H["代表性功能演示"]
    H --> I["四项关键技术"]
    I --> J["四个工程特色/创新"]
    J --> K["团队与工作量佐证"]
```

原稿的表达顺序非常清楚，但中后段有明显“功能、技术、创新分开展示”的特点：先列一轮功能，再列一轮技术，再列一轮特色。这个方式适合展示“全”，但不太适合突出“为什么这个功能必须做、具体解决了谁的问题、技术突破在哪里”。

## 四、原 PPT 的核心分类体系

### 1. 六大模块

- 学生工作
- 校园生活
- 个人画像
- 教务系统
- 3D 校园
- 智能机器人

### 2. 三大支柱

- 孪生驱动：3D 校园
- 智能模块：个人画像、智能机器人
- 业务系统：学生工作、校园生活、教务系统

### 3. 六类服务角色

- 学生
- 教师
- 辅导员
- 院系领导
- 学工领导/学工管理员
- 宿舍管理员

### 4. 其他规模化表达

- 两端适配：PC 端、移动端
- 十余种数据源
- 全生命周期：录取入学、在校教学与生活、毕业离校
- 多角色、多业务、多终端协同

### 5. 四项关键技术

- 数字孪生实景三维校园
- 大数据分析能力
- AI 技术支持与运用
- 云平台服务支持

### 6. 四个工程特色/创新

- 孪生驱动
- 全面性
- 智能化与人性化
- 个性化

> 注：用户口头提到“尹楠的三个支撑，六个创新”，但从截图可确认的原稿命名更接近“六大模块、三大支柱、四项关键技术、四个工程特色”。后续做我们自己的 PPT 时，可以沿用“支柱/创新”的组织感，但不需要机械照搬数量。

### 第 04 页：行业分析

文件：`微信图片_20260804134502.png`

内容：引用《“十四五”国家信息化规划》中关于推动信息技术、智能技术与教育教学融合的方向。页面给出智慧校园市场规模增长曲线：2020 年 614.82 亿元、2021 年 672.91 亿元、2022 年 732.46 亿元、2023E 794.13 亿元、2024E 855.04 亿元、2025E 914.98 亿元、2026E 975.27 亿元。2021 年智慧校园市场结构中，智慧硬件占 72.93%，智慧软件占 27.07%。

叙事作用：用政策和市场规模证明赛道存在，并暗示智慧软件仍有发展空间。

### 第 05 页：行业现状与趋势

文件：`微信图片_20260804134530.png`

内容：页面总结智慧校园发展趋势，包括校园业务全覆盖、泛在应用、大数据助力学生个性化发展、基础设施完善、信息共享能力提升、信息化队伍和教育信息化体系建设。竞品/相关平台包括校宝在线、今日校园、启明星辰、好未来学而思，并分别比较其优势与不足。结论倾向是：智慧校园正在向信息化发展，但资源更多偏向在线教育，智慧管理系统仍有较大完善空间。

叙事作用：从宏观市场落到竞品格局，说明“管理型智慧校园”仍有机会。

### 第 06 页：痛点与问题

文件：`微信图片_20260804134553.png`

内容：中心结论是“智能化管理水平有待提高”。具体痛点包括学业、心理等预警不及时；数据孤岛和数据共享不足；数据分散、不完整、质量参差、缺少数据服务；部门管理松散、流程和应用重复建设；缺少覆盖完整生命周期的管理；过度重视硬件建设而忽视软件投入。

叙事作用：将行业问题转成校园管理场景中的真实矛盾。

## 六、这套参考 PPT 值得保留的讲法

- 前期“政策背景 - 行业现状 - 痛点问题 - 需求分析”的链路很完整，能让评委先接受项目必要性。
- “六大模块、三大支柱、六类角色、两端适配、十余种数据源”这些数字化表达很清楚，适合快速建立平台体量。
- 它不是直接讲技术，而是先展示产品全貌，再解释技术支撑，观众理解门槛较低。
- 功能展示覆盖了视觉冲击、业务流程、AI 智能、数据分析、多端适配，材料类型比较丰富。
- 团队介绍与数字孪生能力之间有对应关系，学科优势不是孤立摆设。

## 七、这套参考 PPT 的主要问题

- 功能、技术、创新被分开讲，同一件事需要观众自己在脑中重新连接。
- 中后段信息密度太高，六大模块、角色树、三大支柱、功能演示、关键技术、工程特色之间有重复。
- 痛点没有和后续核心功能形成一一对应关系，例如“预警不及时”后面对应哪些功能、哪些技术、产生什么效果，没有被连续讲清楚。
- 太多功能被平铺展示，核心创新点被稀释。
- 部分关键技术更像“使用的平台能力或第三方能力”，没有充分区分团队自己的技术突破。
- 第 18 页和第 19 页疑似动画重复页，如果转成正式汇报，需要合并。
- 若要做答辩型 PPT，市场规模、数据量、百万并发等宣称需要进一步加来源或降调处理。

## 八、对我们后续 PPT 的改造原则

用户希望保留这套 PPT 的三个优点：

- 保留前期需求调研、需求分析的铺垫。
- 保留全品类平台功能展示，让评委知道平台不是单一 AI 问答工具。
- 保留“三大支撑/支柱、核心创新”等清晰分组方式。

但后续讲法需要改成“问题驱动的核心功能叙事”：

```mermaid
flowchart LR
    A["真实业务问题"] --> B["业务需求如何确定"]
    B --> C["对应产品功能"]
    C --> D["业务流程如何跑通"]
    D --> E["使用哪些技术"]
    E --> F["技术突破在哪里"]
    F --> G["解决结果与材料佐证"]
```

也就是说，后续不应该像参考 PPT 一样，把“功能展示、关键技术、工程创新”拆成三块重复讲，而应当围绕 3-4 个核心场景，把问题、功能、技术、突破和效果融成一条线。

## 九、推荐复用的核心场景讲法模板

每个核心功能点建议用同一个叙事模板：

| 叙事环节 | 需要回答的问题 |
| --- | --- |
| 角色与场景 | 谁在什么场景下遇到问题？ |
| 真实问题 | 当前业务痛点是什么？为什么传统方式不够？ |
| 需求来源 | 这个需求来自调研、实际教学流程、学生学习行为，还是管理侧反馈？ |
| 功能设计 | 平台做了哪个功能来承接这个需求？ |
| 业务流程 | 用户从进入功能到完成任务的链路是什么？ |
| 技术支撑 | 这里用了哪些模型、Agent、RAG、记忆系统、多模态生成、数据分析或端侧能力？ |
| 技术突破 | 难点在哪里？项目相对普通 AI 工具的增量是什么？ |
| 结果价值 | 对学生、教师、管理员分别带来什么价值？ |
| 材料佐证 | 用截图、流程图、数据表、演示视频、代码结构或测试结果证明什么？ |
| 平台回流 | 这个功能产生的数据如何回到画像、记忆系统或后续推荐中？ |

## 十、后续用于 SparkLearn 的叙事迁移方向

参考 PPT 的“智慧校园平台”可以迁移成 SparkLearn 的“个性化学习多智能体平台”叙事：

- 政策/背景：从智慧校园政策和市场，替换为 AI+教育、个性化学习、教育数字化和学习资源供给压力。
- 痛点：从校园管理痛点，替换为学习路径不个性化、资源制作成本高、AI 回答不可信、学习数据无法回流、教师备课和学情分析压力大。
- 需求分析：从数据/功能/用户/性能四类需求，迁移为学习者数据、学习资源生成、智能辅导、教师管理、可信安全、多端使用等需求。
- 全景展示：保留“平台全功能展示”，但只用 1-2 页讲清楚整体模块。
- 核心场景：聚焦 3-4 个最能体现项目价值的功能闭环，例如学习者画像与记忆系统、学习资源全模态生成、智能辅导与可信回答、学习反馈与能力提升。
- 技术架构：放在核心场景之后，用来解释这些场景共享的底座，而不是提前把技术堆满。
- 创新总结：不再罗列一堆功能名，而是总结为“个性化闭环、多智能体协同、全模态资源生成、可信可控、国产化适配”等少数高记忆点。

## 十一、可直接复用的参考链路

建议后续 SparkLearn PPT 主线采用：

```mermaid
flowchart LR
    A["背景与政策"] --> B["学习场景痛点"]
    B --> C["需求分析矩阵"]
    C --> D["平台全景：模块、角色、端口"]
    D --> E["核心场景 1：画像与记忆"]
    E --> F["核心场景 2：资源生成"]
    F --> G["核心场景 3：智能辅导与可信回答"]
    G --> H["核心场景 4：反馈评测与画像回流"]
    H --> I["系统架构与技术底座"]
    I --> J["核心创新与工程价值"]
    J --> K["材料佐证与总结"]
```

这条链路保留了参考 PPT 的“先铺背景、再讲全貌、再讲技术和创新”的秩序，但把中间最关键的部分改成了“真实问题驱动的核心场景闭环”。这样讲出来会更像一个有因果的项目故事，而不是功能菜单。

# 小程序 AI助学页布局改造与图标系统对齐设计

日期：2026-06-12

## 目标

本次改造包含两个紧密相关的部分：

1. 重构小程序 `AI助学` 页面，使其在空状态下具备“快速开始”能力，在消息状态下保留当前对话能力。
2. 将小程序现有自绘图标系统统一对齐到网页端主平台所使用的同一图标库语义与线性风格。

本次改造明确不做以下事项：

- 不沿用参考图的暗色系，页面继续使用小程序当前浅色体系。
- 不修改小程序 tabbar 的页面结构和文案。
- 不将网页端 `IconBlock` 这种浅色底块包装强制搬到小程序。

## 背景

当前小程序 `AI助学` 页存在三个问题：

1. 空状态结构偏工具页，缺少“刚进入即可快速提问”的首屏组织。
2. 消息态中引用、MCP、研讨会过程等信息拆成多块独立卡片，卡片感过重，打断阅读主线。
3. 小程序使用自绘 `AppIcon`，而网页端主平台使用固定图标库 `lucide-react`，两端图标来源和视觉语义不一致。

用户给出的目标是：

- 借参考图的布局骨架，但不要其暗色风格。
- 空状态中部需要展示固定文案的“快速问题”。
- 快速问题点击后直接发送。
- 输入框上方必须常驻展示全部功能切换。
- 消息下方的调用过程需要收敛成轻量入口，而不是多张大卡片。
- 小程序全部图标应从网页端同一个图标库寻找对应图标，不改页面结构，只换图标。

## 范围

### 包含

- `miniapp/src/pages/tutor` 页面结构和样式重构
- `miniapp/src/components/AppIcon` 图标底座重构
- `miniapp/src/components/AppTabBar` 图标替换
- 小程序中所有当前依赖 `AppIcon` 的页面图标替换为同一套语义映射

### 不包含

- 练习页、我的页、设置页的信息结构重做
- 小程序导航结构重构
- 新增动态推荐问题能力
- 接入网页端 `lucide-react` 运行时依赖本身

## 网页端图标系统调研结论

网页端主平台图标体系结论如下：

- 固定图标库为 `lucide-react`
- 主移动 tab 使用线性图标，常用尺寸为 `20px`
- 常见高频图标尺寸集中在 `16px / 20px / 24px`
- 主导航语义示例：
  - `Home`
  - `User`
  - `Map`
  - `BookOpen`
  - `CheckSquare`
  - `MessageSquare`
- 按钮和统计卡片中广泛使用同一套线性图标语义

因此，小程序图标系统对齐目标不是对齐自定义 SVG 形状，而是对齐 `lucide` 的图标语义和线性描边风格。

## 设计总览

本次改造采用“图标系统底座统一 + AI助学页双态重构”的组合方案。

两者在实现顺序上是串行的：

1. 先统一图标底座
2. 再重构 `AI助学` 页

但作为一次交付整体完成，避免页面改完后因图标系统变化再次返工。

## 图标系统设计

### 总体原则

- 小程序保留 `AppIcon` 作为统一图标入口
- 页面不直接散落维护不同风格图标
- 图标只对齐网页端同一图标库对应语义
- 不改变现有页面结构和文案，只替换图标造型和语义映射

### 视觉原则

- 使用线性风格
- 统一描边粗细
- 统一默认尺寸
- 激活态、普通态、禁用态继续复用现有颜色系统
- 不强制为所有图标增加浅色底块包装

### 语义映射

小程序现有 `AppIconName` 与目标图标语义映射如下：

- `bot` → `Bot`
- `sparkles` → `Sparkles`
- `users` → `Users`
- `globe` → `Globe`
- `cpu` → `Cpu`
- `shield` → `Shield`
- `image` → `Image`
- `mic` → `Mic`
- `send` → `Send`
- `plus` → `Plus`
- `book` → `BookOpen`
- `quiz` → `CheckSquare`
- `user` → `User`
- `folder` → `Folder`

### 组件策略

`AppIcon` 继续保留 `name` 接口，不改变调用方 API。实现方式改为更接近 lucide 风格的统一结构，保证：

- 调用方几乎不需要改动
- tabbar、header、按钮等现有使用点可平滑替换
- 后续新增图标仍通过统一入口扩展

### 覆盖范围

本次至少覆盖：

- `AppTabBar`
- `AI助学` 页全部按钮
- 使用 `AppIcon` 的 header 按钮
- 其他使用 `AppIcon` 的页面入口图标

如果某些页面当前未使用 `AppIcon` 而是纯 CSS 画图，本次不主动重构其信息结构，但若与统一图标底座直接冲突，则一并收口。

## AI助学页布局设计

### 页面状态

页面分为两种状态：

1. 空状态：当前还没有消息，展示快速开始布局
2. 消息状态：已有消息，展示对话布局

两种状态共用同一套底部固定交互区。

### 顶部区域

顶部保持当前职责不变：

- 左侧/中间显示当前角色
- 右侧提供新建对话入口

顶部不新增复杂入口，避免首屏抢焦点。

### 空状态布局

空状态借参考图的骨架，但不使用暗色视觉：

- 中心标题
- 一句简短说明
- 中部快捷问题区

快捷问题区要求：

- 使用轻量气泡列表，而不是厚重卡片
- 文案固定写死
- 点击后直接发送
- 不需要先填入输入框再确认

快捷问题示例文案在实现时以 4 到 8 条为宜，优先围绕高频学习提问，而不是跳转型入口。

空状态中不保留参考图中的：

- `AI创作`
- `去练习`
- `我的`

原因是这些入口和当前 `AI助学` 页主任务不匹配，会稀释“快速发问题”这一核心目标。

### 底部固定区

底部固定区在空状态和消息状态下完全一致，包含两层：

1. 功能切换区
2. 输入操作区

#### 功能切换区

功能切换区常驻可见，展示全部现有模式：

- 模型选择
- 研讨会
- 联网搜索
- MCP 模式
- 可信模式
- 图片模式

要求：

- 不折叠
- 不隐藏到二级面板
- 输入框上方始终可见
- 允许横向或多行排布，但必须保证一眼可见全部功能

#### 输入操作区

输入操作区固定到底部，保留：

- 文本输入
- 文件上传
- 语音输入
- 发送

要求：

- 始终固定在 tabbar 上方
- 安全区留白正确
- 在空状态和消息状态下位置一致

### 消息状态布局

消息状态下，中部区域从空状态切换为消息流。

设计原则：

- AI 正文是主阅读对象
- 过程信息不得再以多个独立重卡片打断正文

### 过程信息收敛策略

当前页面中的以下信息将统一收敛：

- 引用来源
- MCP 调用
- 研讨会过程
- 其他过程性辅助信息

新的表现方式：

- 不使用“回答依据与过程”这类重标题
- 在 AI 消息正文下方只显示一行轻量摘要入口
- 示例形式：
  - `引用 2 · MCP 1 · 研讨会 3 · ...`

交互要求：

- 无过程信息时不显示
- 有过程信息时显示摘要入口
- 用户点击后再展开附属内容

展开后的内容仍属于当前消息的附属区域，而不是页面级独立卡片区。

### 消息正文与附属区关系

消息结构分为两层：

1. 主消息层
   - AI 正文
   - 播放按钮
   - 必要时的轻量状态信息
2. 附属信息层
   - 通过一行轻量摘要入口进入
   - 展开后展示引用、MCP、研讨会等细项

这样可以减少页面碎片化，保持消息主线清晰。

## 数据与状态策略

### 空状态判定

空状态不根据“欢迎消息对象是否存在”判定，而根据“是否已有真实对话消息”判定。

实现时应避免默认欢迎消息导致页面永远无法进入空状态布局。

### 快捷问题发送

快捷问题点击后直接复用现有发送流程：

- 生成用户消息
- 创建或复用会话
- 进入流式返回
- 切换到消息态

### 功能切换状态

功能切换区继续复用当前页面已有状态字段：

- `modelName`
- `workshopEnabled`
- `webSearchEnabled`
- `mcpEnabled`
- `trustModeEnabled`
- `imageModeEnabled`

改造只调整它们的展示布局，不改变状态语义。

## 错误处理

### 图标系统

- 如果某个网页端图标语义在小程序中没有直接一一对应，则选择最接近语义的 lucide 图标
- 不为少量个例引入第二套图标来源

### AI助学页

- 快捷问题发送失败时，继续沿用当前发送失败提示
- 过程信息缺失时，不显示入口，不显示空容器
- 功能切换区在窄屏换行时，应优先保证可读性，不得遮挡输入框

## 测试策略

### 图标系统验证

- 校验 `AppIcon` 每个已映射名称都能正常渲染
- 校验 tabbar 激活态与普通态图标显示一致
- 校验按钮图标在普通态、激活态、禁用态下不变形

### AI助学页验证

- 无消息时展示空状态布局
- 快捷问题点击后直接发送并切到消息态
- 有消息时展示消息流
- 过程信息入口正确出现与展开
- 输入框固定到底部
- 全部功能切换始终可见
- 微信小程序 WebView 渲染模式下不使用不兼容能力

## 实施顺序

1. 重构 `AppIcon`
2. 替换 `AppTabBar` 与使用 `AppIcon` 的图标
3. 重构 `AI助学` 页空状态与消息态结构
4. 收敛过程信息到消息下方轻量入口
5. 验证构建与关键页面显示

## 风险与约束

### 风险

- `AI助学` 页当前文件体量偏大，结构调整时容易引入状态分支混乱
- 现有默认欢迎消息可能干扰双态判定
- 图标替换若只改视觉不改布局，部分按钮尺寸可能需要顺带微调

### 约束

- 不做无关页面重构
- 不新增动态快捷问题逻辑
- 不修改 tabbar 信息架构
- 不引入第二套图标风格

## 结论

本次交付将通过统一小程序图标底座和重构 `AI助学` 页双态结构，解决：

- 小程序与网页端图标系统不一致
- `AI助学` 页空状态不好用
- 消息态过程信息卡片过重

最终效果应满足：

- 图标统一来自网页端同一图标库语义
- 空状态可快速直接发问
- 全部功能切换常驻可见
- 过程信息收敛到消息下方轻量入口
- 页面整体保持浅色、简洁、可读
